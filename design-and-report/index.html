Project 27: Analytics Engineering Mini-Warehouse

Tujuan project: membangun mini data warehouse yang mengubah file produksi harian menjadi KPI yield, NG rate, dan rework rate yang konsisten, teruji, dan ter-update otomatis setiap hari, sehingga laporan tidak lagi disusun dengan copy-paste dan setiap angka bisa dilacak asalnya.

Kategori:Rancangan projectManufaktur lampu LEDData simulasidbt + SQL + otomasi

Project Introduction

Bayangkan dapur pusat sebuah jaringan restoran. Setiap pagi bahan mentah datang dari pemasok. Bahan dicuci dan dipotong dengan cara yang sama, lalu dimasak memakai resep baku agar rasa di semua cabang sama. Sebelum dikirim, setiap masakan dicicipi. Jika ada yang tidak sesuai, masakan ditahan dan cabang tetap menerima masakan kemarin yang sudah pasti benar.

Tanpa dapur pusat, setiap cabang memasak dengan resepnya sendiri. Rasanya berbeda-beda, dan tidak ada yang tahu bahan mana yang membuat masakan gagal. Pemilik restoran ingin satu dapur dengan resep baku, pemeriksaan rasa yang tidak pernah terlewat, dan jadwal yang berjalan sendiri setiap pagi.

Project ini membangun pipeline KPI produksi yang teruji dan berjalan otomatis: file mentah dimuat ke database, dirapikan dan dihitung dengan model dbt, diperiksa dengan data tests, lalu dashboard dan laporan diperbarui setiap hari. Datanya simulasi, karena data pabrik bersifat rahasia. Kata bergaris bawah putus-putus kuning bisa diklik untuk melihat artinya.

Gambaran alur kerja di pelaporan KPI produksi lampu LED

Pelaporan KPI bisa dibayangkan sebagai tiga jalur. Dua jalur pertama sudah berjalan di pabrik saat ini. Jalur ketiga adalah yang dibangun di project ini.

  1. File produksi. Setiap stasiun mencatat jumlah input, OK, NG, dan rework setiap hari. Filenya terkumpul di folder bersama, seperti bahan mentah yang datang dari pemasok.
  2. Laporan manual. Setiap minggu seseorang menyalin data ke Excel rekap dan menghitung yield dengan rumusnya sendiri. Akibatnya angka di laporan yang berbeda bisa tidak sama.
  3. Staging dan mart. Data dirapikan dengan satu cara standar, lalu KPI dihitung dengan satu resep baku berupa model SQL di dbt. Semua laporan memakai hasil yang sama.
  4. Data tests sampai dashboard. Setiap hasil diperiksa otomatis. Jika lulus, dashboard dan laporan diperbarui. Jika gagal, versi terakhir yang benar dipertahankan dan alert dikirim.

1. BackgroundKenapa tema ini dipilih

Latar belakang masalah

Di pabrik lampu LED, laporan KPI mingguan dan bulanan masih disusun dengan copy-paste dari file harian ke Excel. Setiap penyusun punya file dan rumusnya sendiri. Akibatnya:

  • Yield yang sama bisa berbeda di dua laporan karena rumus berbeda, misalnya rework dihitung atau tidak dihitung sebagai OK.
  • Data ganda, NG yang kosong, atau kode stasiun salah ketik ikut terhitung tanpa ketahuan, sehingga KPI tampak lebih baik dari kenyataannya.
  • Laporan baru tersedia setelah seseorang sempat menyusunnya. Penurunan yield terlambat diketahui.
  • Saat ada pertanyaan "angka ini dari mana?", jawabannya harus dicari ulang di banyak file.

Alasan memilih tema ini sebagai portofolio

  • Dekat dengan pekerjaan sehari-hari. Menyusun laporan output, yield, dan rework adalah pekerjaan rutin di bagian proses, sehingga kebutuhan dan jebakannya dipahami dengan baik.
  • Menunjukkan skill analytics engineering. Pemodelan data berlapis dengan dbt, data tests, dokumentasi lineage, dan otomasi terjadwal. Skill ini makin sering diminta di lowongan Data Analyst.
  • Tingkat kesulitan lanjut. Analisisnya deskriptif, tetapi merancang lapisan model, test, jadwal otomatis, dan pipeline yang bisa dibangun ulang dari nol butuh disiplin rekayasa.
  • Terhubung dengan project lain. Memakai definisi KPI dari Project 3 (Yield, Rework & Defect Tracking) dan bisa menerima tabel tidy dari Project 25 (Messy Excel Report Parser). Mart KPI-nya bisa menjadi sumber Project 23 (Telegram Bot KPI Reporting) dan Project 29 (Root Cause Analysis Statistik).

4. DatasetData simulasi buatan sendiri yang meniru file produksi harian pabrik lampu LED

Kenapa data simulasi? Data pabrik bersifat rahasia. Program Python membuat file harian yang meniru pola nyata: stasiun yang lebih sering NG, pengaruh shift dan model, file yang terlambat, dan data kotor. Karena kejadian yang ditanam diketahui, kita bisa memeriksa apakah test dan analisis berhasil menemukannya.

Ukuran: 10 stasiun, 3 model, 2 shift, sekitar 20 operator, sekitar 150 hari kerja (6 bulan), satu file per hari. Perkiraan jumlah baris: ±9.000 baris produksi, ±15.000 baris defect, dan ±1 baris per unit rework. Untuk benchmark, data diperbesar menjadi ±1 juta baris. Jumlah pastinya baru diketahui setelah data dibuat.

Sumber data: data simulasi buatan sendiri, dibuat oleh skrip scripts/generate_raw.py di repositori project (Versi: v1; Tanggal dibuat: 28 Okt 2026; Seed: 27260302). Tidak memakai dataset publik atau data perusahaan.

Fakta yang sengaja ditanam (ground truth)

1. Burn-in Test dibuat paling sering NG, didominasi kegagalan driver.

2. Satu lonjakan NG di Photometric Test selama ±1 minggu, misalnya akibat ganti lot chip LED.

3. Di bulan ke-4, file mentah menambah satu kolom dan mengganti nama kolom lain, sehingga test skema harus gagal.

4. Satu file harian terlambat masuk 2 hari, sehingga test kesegaran data harus memberi peringatan.

5. Sekitar 2–3% data kotor: baris ganda, NG kosong, kode stasiun salah ketik, dan format tanggal berbeda.

Model dbt yang akan dibuat

Model disusun berlapis, seperti tahapan di dapur: bahan mentah, bahan yang sudah dicuci dan dipotong, lalu masakan jadi. Dashboard hanya membaca lapisan terakhir, sehingga semua laporan memakai angka yang sama.

5. ToolsAlat yang dipakai dan alasannya

dbt-duckdb

Menulis model SQL berlapis (staging, mart), data tests, dan dokumentasi lineage dalam satu project. Satu perintah membangun ulang semuanya.

dbt adalah alat standar analytics engineering. Adapter DuckDB membuatnya bisa jalan tanpa server.

DuckDB + SQL

Database tempat semua lapisan disimpan. SQL dipakai untuk semua perhitungan KPI di dalam model dbt.

Gratis, tanpa server, satu file. Konsisten dengan project lain di portofolio ini.

GitHub Actions

Menjalankan pipeline sesuai jadwal (cron): muat data, dbt build, test, lalu perbarui dashboard dan laporan.

Gratis untuk repositori publik dan tidak perlu server sendiri.

Python (Polars, pandas)

Membuat data simulasi, memuat file mentah, dan menjalankan benchmark kecepatan (Q9).

Polars dipakai untuk membandingkan kecepatan dengan pandas pada data besar.

Streamlit + Plotly

Dashboard yang membaca mart KPI: ringkasan, yield per stasiun, Pareto defect, dan status data tests terakhir.

Semua tetap di Python. Looker Studio di daftar portofolio tidak dipakai agar seluruh alur ada di satu repositori.

Quarto (opsional)

Membuat laporan KPI mingguan HTML atau PDF secara otomatis dari mart.

Bisa diganti template HTML sederhana jika waktu terbatas.

Excel

Cek silang: menghitung ulang KPI secara manual pada sampel hari dan stasiun (Q2).

Alat yang sudah biasa dipakai di pabrik, jadi hasilnya mudah diverifikasi rekan kerja.

GitHub

Menyimpan kode, model dbt, workflow, dan README.

Standar industri untuk portofolio dan riwayat perubahan kode.

Markdown

Menulis README, definisi KPI, dan deskripsi model dbt.

Format teks sederhana yang tampil rapi otomatis di GitHub dan di dbt docs.

Tahap A · Perencanaan

  1. Menyepakati definisi KPI

    Menetapkan rumus FPY, RTY, NG rate, rework rate, dan scrap rate, serta aturan kapan unit dihitung OK, NG, rework, atau scrap.

    Hasil: dokumen definisi KPI · Alat: Markdown

  2. Merancang lapisan model dan test

    Menentukan 8 model dbt, hubungan antar model, dan test yang wajib untuk setiap kolom penting.

    Hasil: diagram lapisan dan daftar test · Alat: Markdown

Tahap B · Menyiapkan data

  1. Membuat data simulasi

    Program Python membuat ±150 file harian dengan pola realistis, termasuk fakta yang ditanam, perubahan kolom di bulan ke-4, dan data kotor 2–3%.

    Hasil: folder file mentah, skrip generator, catatan ground truth · Alat: Python

  2. Memuat file mentah

    Memuat semua file ke lapisan raw tanpa diubah, mendaftarkannya sebagai source dbt, dan menambahkan aturan kesegaran data.

    Hasil: tabel raw dan konfigurasi source · Alat: Python, DuckDB, dbt

  3. Membuat model staging

    Merapikan nama kolom, tipe data, format tanggal, dan kode stasiun; membuang baris ganda dengan aturan yang dicatat (Q6).

    Hasil: 3 model staging · Alat: dbt, SQL

Tahap C · Menghitung dan menganalisis

  1. Membuat model mart KPI

    Menghitung KPI harian per stasiun, Pareto defect mingguan, dan KPI lini mingguan, lalu menjawab Q1 dan Q3–Q5.

    Hasil: 3 model fakta dan 2 dimensi · Alat: dbt, SQL

  2. Menulis data tests

    Menambahkan test not_null, unique, accepted_values, relationships, rentang nilai, dan freshness, lalu memeriksa apakah semua fakta yang ditanam tertangkap (Q6, Q7, Q13).

    Hasil: laporan hasil test · Alat: dbt

  3. Cek silang dengan Excel

    Menghitung ulang KPI secara manual untuk beberapa hari dan stasiun, lalu memastikan hasilnya sama dengan mart (Q2).

    Hasil: lembar cek silang · Alat: Excel

  4. Menjalankan pipeline sesuai jadwal

    Membuat workflow GitHub Actions yang menjalankan dbt build setiap hari, menyimpan log, dan mengirim alert jika gagal. Menguji pembangunan ulang dari nol (Q8, Q14).

    Hasil: file workflow dan riwayat run · Alat: GitHub Actions

  5. Benchmark dan menghitung dampak

    Membandingkan kecepatan pandas, Polars, dan DuckDB pada data besar, lalu menghitung jam penyusunan laporan yang dihemat dengan label estimasi (Q9, Q11, Q12).

    Hasil: tabel benchmark dan skenario dampak · Alat: Python

Tahap D · Menyajikan

  1. Membuat dashboard dan laporan otomatis

    Dashboard 4 halaman: Ringkasan, Yield per Stasiun, Pareto Defect, dan Status Data. Laporan mingguan HTML/PDF dibuat otomatis setelah test lulus.

    Hasil: link dashboard dan laporan · Alat: Streamlit, Plotly, Quarto

  2. Menerbitkan dbt docs dan README

    Menerbitkan dokumentasi lineage (Q10), menulis README dengan diagram alur data dan hasil test, lalu memperbarui checklist di daftar portofolio.

    Hasil: situs dbt docs dan repositori siap ditinjau · Alat: dbt, Markdown, GitHub

8. Success CriteriaKomponen tambahanKapan project dianggap selesai dan berhasil

Project dianggap berhasil jika

  • Kesembilan pertanyaan berlabel "Utama" terjawab dengan angka dari data.
  • KPI dari mart sama dengan hitungan manual Excel pada sampel yang dicek.
  • Semua test lulus pada data bersih, dan test yang tepat gagal pada fakta yang ditanam (perubahan kolom, file terlambat, data kotor).

7. KesimpulanHasil analisis, Impact, success criteria, rekomendasi, saran perbaikan, dan batasan

7.1 Hasil analisis

Pertanyaan utama: KPI produksi bisa dibuat konsisten, teruji, dan dibangun ulang otomatis: satu definisi di model dbt, 60 data test, dan gerbang publish yang menahan hasil jika skema berubah. Cek silang dengan Excel sama pada semua 300 pemeriksaan, sedangkan rekap manual dari raw meleset sampai 2,5 poin FPY. Bagian yang belum terbukti adalah eksekusi terjadwal oleh GitHub Actions selama 7 hari.

  • Burn-in Test stasiun terburuk (NG rate 3,70%); RTY lini 90,2%, final yield 93,7%.
  • Minggu 2026-06-08 turun (RTY 86,9%) karena Photometric Test; 5 hari lonjakan berturut-turut.
  • Shift tidak berpengaruh (p = 0,76); model berpengaruh kecil (12W 1,17%, 5W 0,91%).
  • Defect dalam satu stasiun terbagi merata; tidak ada defect dominan.
  • 300 dari 300 baris kotor tertangkap; kelima fakta yang ditanam terdeteksi.

7.2 Impact (estimated, simulated)

Penyusunan laporan manual sekitar 78 jam per tahun pada asumsi 90 menit × 52 laporan; rentang 52 sampai 104 jam. Angka ini asumsi.

7.4 Rekomendasi

  • Fokuskan perbaikan proses pada Burn-in Test, stasiun dengan NG rate tertinggi.
  • Jadikan dbt build gerbang wajib sebelum KPI dipublikasikan; perubahan nama kolom harus menghentikan pipeline atau memicu peringatan, bukan hilang diam-diam.
  • Standarkan template Excel produksi (kolom terkunci, validasi angka, daftar pilihan stasiun) agar data kotor tidak masuk.
  • Catat rework per unit (nomor lot atau serial) agar analisis penyebab bisa dilanjutkan di Project 29.

7.5 Saran perbaikan

  • Gabungkan ke main setelah ditinjau, lalu biarkan GitHub Actions berjalan 7 hari untuk memenuhi kriteria 4.
  • Deploy dashboard ke Streamlit Community Cloud dan uji ke satu pembaca awam untuk kriteria 5 dan 6.
  • Tambahkan data kotor berformat tanggal berbeda dan defect dominan pada generator versi berikutnya agar Q3 bisa menunjuk penyebab.

7.6 Batasan

  • Semua temuan berasal dari data simulasi; fakta yang ditemukan adalah fakta yang ditanam sendiri.
  • Data test hanya menangkap aturan yang ditulis; kesalahan yang tidak terpikirkan tetap bisa lolos.
  • Rework hanya per hari, stasiun, dan model; tidak ada lot atau serial. Nama defect dan nama stasiun berbeda dari rancangan.
  • Waktu benchmark dan durasi run bergantung pada mesin. Jam hemat adalah asumsi menit per laporan.
